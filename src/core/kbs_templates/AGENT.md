# 业务知识库操作规范

本文件是知识库根目录下的详细工作流规范：执行收录、决议、回写、整理等写入操作前，先读对应章节并严格按步骤执行。
意图识别、自主边界、会话启动与检索顺序由系统协议（kbs preamble）承载，本文件不重复。
所有相对路径相对知识库根目录。

## 知识模型

- `raw/sources/`：原始材料的不可变快照（仅追加）
- `wiki/active.md`：当前工作、进行中的对比分析、待决问题
- `wiki/recent.md`：最近新增、更新、修正或已过时的知识
- `wiki/index.md`：先按业务领域、再按页面类型分组的目录
- `wiki/log.md`：按时间顺序记录的收录、回写、查询、整理操作
- `wiki/domains/`：业务维度层——每条业务线一个中心页 + `index.md` 受控词表注册表
- `wiki/concepts/`：稳定的概念、定义、方法、框架
- `wiki/entities/`：人物、组织、产品、工具、数据集、命名系统
- `wiki/insights/`：持久结论、对比分析、决策记录、综合要点
- `meta/candidates/`：临时工作记忆笔记，后续可提升、合并或丢弃
- `meta/lint-status.json`：健康度与新鲜度元数据
- `meta/schemas/`：页面模板（domain / concept / entity / insight / candidate），创建和更新页面时参照

分区方式：`entities/` 数量大、天然按领域划分 → 按主域分子目录；`insights/`、`concepts/` 数量少、常跨领域 → 扁平 + `domain` 字段；`candidates/` 临时 → 扁平 + 可选 `domain` 标签。

## 领域规则

业务维度是**受控词表**，不是自由标签：领域 slug、中文名、别名、一句话定位规范地列在 `wiki/domains/index.md` 注册表中。注册表是有效 slug 的唯一事实来源——每个页面的 `domain` 值必须出现在那里。

归属刻意分开：

- **用户拥有分类法**：创建、合并、拆分或退役领域属结构性变更，只建议，未经明确确认不执行。
- **Agent 拥有页面**：分配/修正 `domain` 字段、保持领域中心范围最新、创建领域子目录、添加交叉链接，是授权回写时的例行维护。

物理位置与 `domain` 字段：

- **物理目录 = 主领域（唯一）**：页面 `domain` 字段多值，**第一个是主领域**；实体放在主领域的子目录，跨域且无明确主域时放 `_shared/`。目录名与 slug 一对一相同，唯 `_shared/` ↔ `cross-cutting`。物理目录只是浏览便利，不捕捉全貌。
- **跨领域页面**物理上放主领域目录，但必须在其涉及的每个领域中心被引用。
- 材料不能干净归入已注册领域时：选最接近的现有领域放置；明显属于另一条业务线时**建议**开设新领域，不自动创建。
- 领域中心的范围部分是活清单：整理时对照声明了该领域的页面核对；长期只有一两个页面的领域，整理时建议合并到相邻领域，不未经确认就合并。
- Slug 约定：小写、连字符、英文（如 `data-governance`）；每个领域有规范中文别名和可选短别名，用于自然语言解析。
- Slug 漂移（错字、同义词、过期 slug）属内容修正而非结构变更：整理时直接修正为已注册 slug，无需询问。

## 收录触发

用户分享以下内容时**主动提供**收录：

- 用于学习或研究的 URL、文章、论文、报告、会议纪要或本地文件
- 有未来复用价值的大段粘贴笔记或文本
- 应纳入长期研究上下文的材料

**不自动收录**：仅用于即时排障的包仓库页面、API 文档、Stack Overflow 链接、bug 报告；没有学习意图的随手链接；临时日志、草稿或一次性执行追踪。

对链接做总结、翻译或提取要点不等于收录；只有用户要求记录以备后用时才捕获。

## 收录工作流

当用户明确要求收录、吸收、保存或记录原始材料以备后用时执行：

1. 读取原始材料。
2. 提取 3-5 个关键要点。
3. 仅当材料内容丰富且预期侧重实质性影响路由，或收录范围确实模糊时，与用户确认要点。
4. 在 `raw/sources/` 保存原始快照。
5. **从注册表中确定主领域**（及任何次要领域），它决定：
   - `domain` frontmatter 字段（多值，所有涉及的领域）
   - 实体的物理目录（主领域子目录；跨域且无明确主域时 `_shared/`）
6. 将稳定内容路由到正确的页面类型：`concept`（稳定的思想和框架）、`entity`（命名的具体事物）、`insight`（持久结论和综合分析）。
7. 对话中同时产生的高价值但尚未稳定的工作记忆，捕获到 `meta/candidates/` 而非强行写入正式 wiki；领域已明确时加可选 `domain` 标签。
8. 按 `meta/schemas/` 中的页面结构创建或更新相关页面。
9. **保持领域中心同步**：页面 `domain` 字段列出的每个领域都在其中心的范围部分引用该页面；主领域还没有子目录时创建它。
10. 添加或刷新交叉链接。
11. 按需更新 `wiki/active.md`、`wiki/recent.md`、`wiki/index.md`、`meta/candidates/index.md`、`wiki/log.md` 和 `meta/lint-status.json`（见「元数据更新」）。

## 写入执行与澄清

写入授权明确后直接执行工作流并简要汇报结果，不在每个中间步骤停下来请求许可。仅以下情况问一个简短的澄清问题：

- 多个主题、候选、领域或目标页面都可能适用
- 不确定用户是要分析还是要写入
- 请求暗示删除、归档、批量清理、大规模结构重组、领域级变更或其他高影响维护操作

## 查询工作流

1. 按 preamble 的检索顺序读取；用户提到一条业务线时，先经 `wiki/domains/index.md` 的别名映射到 slug，走该领域中心路由。
2. 先读直接相关的页面，再回退到原始来源。
3. `meta/candidates/` 仅作补充线索：提示值得验证的暂定假设、恢复最近但未解决的工作、指向需确认的页面、来源或待决问题。
4. 回答时附明确的文件引用。
5. 区分稳定的 wiki 结论与暂定的候选线索；不把候选笔记作为最终结论的唯一依据（除非用户明确要求查看暂定材料）。
6. 用户请求已暗示回写、提升、合并、丢弃或维护时直接执行；否则建议相关回写，不自动持久化。

## 候选规则

`meta/candidates/` 是高价值但尚不够稳定进入正式 wiki 的缓冲区，不是一等真相源。

适合捕获：可能改变业务线方向或重新定义待决问题的材料；有明确未来复用价值但尚需验证或整合；可与已有的来源、领域、概念、实体或洞察关联。

不捕获：人格笔记、无复用结构的随意猜测、临时任务跟踪、原始聊天记录。

- 一次强有力的对话观察本身不足以创建候选——除非用户要求保留，先建议候选捕获。
- 创建新候选前先检查 `meta/candidates/index.md` 和相关开放笔记，优先更新已有候选。
- 审查 `open` 候选的时机：用于回答时、相关正式页面变更时、整理时、创建/更新后 7 天内。
- `open` 候选 14 天无审查、更新、提升、合并或丢弃视为过期；过期不等于自动删除——下次整理默认解决，仍有明确复用价值则刷新 `updated` 并使 `next_action` 更具体。

## 候选决议工作流

- `promote`（提升）：将笔记转为新的或实质修订的正式页面（通常为 `insight`），候选状态置为 `promoted`
- `merge`（合并）：将持久部分合并到已有的 `insight`、`concept` 或 `entity` 页面，候选状态置为 `merged`
- `drop`（丢弃）：不再有长期复用价值时，状态置为 `dropped`

决议更新要求：

- 始终更新候选笔记状态和 `updated`
- 始终刷新 `meta/candidates/index.md`
- `promote` 或 `merge` 时更新目标正式页面
- `promote`/`merge` 后刷新 `wiki/recent.md`；`drop` 仅在活跃工作被实质改变时刷新
- 新增页面或可发现性链接变更时刷新 `wiki/index.md`
- 结果改变活跃论点、活跃业务线或待决问题时刷新 `wiki/active.md`
- 页面在某领域被新增、移动或删除时刷新该 `wiki/domains/<domain>.md` 中心范围
- 在 `wiki/log.md` 追加简短维护记录
- 更新 `meta/lint-status.json` 反映维护操作

## 回写规则

仅在用户要求记录结果或请求已包含明确写入授权时执行回写；否则简要建议回写，保持知识库不变。

回写**持久知识**：有力的对比或综合分析、稳定的定义或框架、业务线论点/研究方向/待决问题/已验证的死胡同、决策记录、可复用洞察、可能帮助未来工作的澄清。

不回写：日常闲聊、人格偏好或语气记忆、原始聊天记录、临时任务状态、无明确复用价值的临时猜测或调试细节、应作为已有页面更新的重复内容。

材料有前景但仍不稳定时，优先用候选笔记而非污染正式 wiki。优先更新已有页面而非创建近似重复；拿不定时，创建或更新 `insight` 页面，或使用候选笔记，而不是存储整个聊天记录。

## 整理工作流

先读 `meta/lint-status.json`。`last_lint` 超过 24 小时，或用户分享的工作可能很快受益于一次维护时，主动建议整理。

用户明确要求维护、健康检查、过期候选审查或请求明确包含维护意图时执行，尤其是：批量收录或多个正式页面更新后；创建、决议或积累多个候选后；依赖较旧的领域中心或洞察页面做新的主题级综合、建议或路线图之前。

定期检查知识库：

- 页面之间的矛盾
- 被更新来源取代的过时结论
- 无有效入站引用的孤立页面
- 反复出现但缺少页面的概念、实体或洞察
- 缺失的交叉链接
- 索引不匹配
- 合并重复页面的机会
- 应提升、合并或丢弃的过期候选

### 领域专项检查

- **字段有效性**：每个页面的 `domain` 值都出现在 `wiki/domains/index.md` 中；错字、同义词和过期 slug 直接修正为已注册的 slug（内容修正，无需询问）。
- **目录一致性**：每个实体的物理目录匹配其主（第一个）`domain` 值，在下一次写入时核对。
- **中心范围核对**：每个 `domains/<domain>.md` 中心列出的页面与声明了该领域的页面精确对应；跨领域页面必须出现在其涉及的每个中心中。
- **孤立集群**：围绕某个主题的实体集群没有匹配的领域，暗示需要新领域——提出建议，不自动创建。
- **近似重复或近似空的领域**：建议合并小的或语义重叠的领域；不未经确认就合并。
- **注册表漂移**：领域中心存在但其 slug 在注册表中缺失（或反过来），标记不一致。

整理时，把 `meta/candidates/index.md` 和开放候选当显式维护队列而非永久积压：过期候选默认在该轮解决，仅当仍有明确复用价值才保持开放（刷新 `updated`、使 `next_action` 更具体）。

删除、归档、批量清理、大规模结构变更、领域变更或目录变更前必须询问用户。

## 依据规则

- 不编造知识库或明确外部来源不支持的知识；尽可能保持来源引用明确。
- 标注矛盾和不确定性，而非隐藏。
- 用户想保留的好答案不应消失在聊天记录中。

## 文件约定

- 领域和文件使用小写、连字符分隔的 slug；页面标题保持人类可读。
- 每个页面顶部放简短摘要；保持交叉链接明确。
- 优先使用纯 markdown 和简单 frontmatter。

## 元数据更新

- 时间字段使用 `YYYY-MM-DD`、`YYYY-MM-DDTHH:MM:SSZ` 或带显式 UTC 偏移的 ISO 8601 格式。
- 新增原始材料时更新 `last_ingest`。
- 从查询、综合、提升或合并回写持久知识时更新 `last_writeback`。
- 每次整理或候选清理时更新 `last_lint`、递增 `lint_count`、尽可能重计 `total_pages` 和 `total_sources`。
- 在 `wiki/log.md` 中记录维护结果，包含日期和具体操作，尤其是候选审查和 `promote` / `merge` / `drop` 结果。
